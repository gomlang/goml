# Performance explanations and reproducible PGO builds

[English](performance.md) | [简体中文](performance.zh-CN.md)

GoML compiles through ANF into Go. Compiler facts and downstream decisions are different evidence: a generated copy may be eliminated, a generated closure may stay on the stack, and a syntactic index may lose its bounds check. Static call counts are not execution counts.

## Explain a build

Run from a GoML module:

```sh
goml build --explain-performance
goml build --explain-performance --format json > performance.json
```

The option forces linking even when package artifacts are cached. It leaves ordinary generated Go unchanged. Default builds do not collect or print the report. Each link writes `goml_generated.go.performance.json`; JSON stdout wraps the reports in `{"version":1,"kind":"goml-performance-build","reports":[...]}` for modules with multiple executables. Build progress and diagnostics remain on stderr.

Each report has `version: 1`, `kind: "goml-performance"`, the compiler version, the generated source SHA-256, `functions`, `sources`, `events`, and `limitations`. Categories identify their producing `stage`, explain their `reason`, and label `certainty`. `source_precision` is `enclosing-declaration`: source entries contain the canonical package, package-relative file name, enclosing declaration line/column, and byte range. This locates the source function, not necessarily the exact costly expression. Generated function names and origins allow inspection of generated Go, but are not a stable ABI across compiler versions or unrelated declaration changes.

The report includes:

- Generated bytes per function and source declaration. These count formatted function declarations, excluding method wrappers, global variables, types, and separators. Source totals can overlap for shared adapters.
- Concrete specialization counts before final pruning. Each ordinary monomorphic function counts as one; entry adapters or other concrete functions attributed to the same declaration can increase its total. This is not a count of distinct type-argument lists or the final number of live target functions.
- ANF inline decisions, including acceptance, reason, candidate cost, cost limit, and remaining caller budget. Current limits are 16 or 32 cost units with an initial caller budget of 48; there is no module-wide inline budget.
- Selected static backend counts: aggregate value bindings, borrowed field projections, indexing expressions, recognized function-value or vtable calls, function literals, and shared-continuation regions. Shared continuations count generated structured exit regions, not source loops or runtime iterations. These are not a complete operation census.

Go escape analysis, Go inlining, retained bounds checks, and runtime allocations are explicitly unmeasured. `borrowed-projection` describes an internal code-generation choice, not a source-language ownership rule. Consult the exact recorded Go toolchain's diagnostics or measured allocations for downstream decisions. The report does not turn an emitted object into an allocation claim or infer optimization advice from unverified costs.

## Field and array copy elimination

GoML has value semantics and shared handles, without Rust-style exclusive borrowing or lifetime syntax. Large named-struct and fixed-array field reads can use generated Go pointers when the local root and binding are not assigned or reused as join parameters. Read-only indexing can then access original immutable storage without copying the containing array.

Assignments, returned values, and closure environments retain ordinary value snapshots. Adjacent, single-use field and array projections can narrow a temporary snapshot to the value actually read. This includes `Ref.get()` and verified forwarding getters: `reference.get().nested.flag` can load the flag directly, and immediate indexing can avoid copying the containing array. The transformation does not cross intervening statements, effectful index expressions, retained snapshots, or escaping addresses. `Vec` lookup still materializes its element snapshot. Embedded `Ref` and `Vec` handles still share their storage. Constant array indexes retain bounds-panic semantics. Generated pointer syntax alone does not establish zero allocations; inspect the report and measure the actual workload.

## PGO input and build records

```sh
goml build --pgo off
goml build --pgo profiles/representative.pgo
goml run --pgo profiles/representative.pgo -- application-arguments
goml build --pgo auto
GOOS=js GOARCH=wasm CGO_ENABLED=0 goml build --pgo profiles/representative.pgo
```

`--pgo off` explicitly disables Go PGO. A path is resolved relative to the GoML module root. `--pgo auto` selects the module root's `default.pgo`, or explicitly disables PGO when it is absent; this avoids depending on the generated file's artifact directory. The option is forwarded to the actual Go build, including native SIMD compilation. Without `--pgo`, existing Go environment behavior is preserved, including `GOFLAGS` and Go's own automatic selection.

Every explicit `--pgo` writes `<executable>.build.json`. `--build-record` also enables a record while preserving inherited PGO configuration. For a fully identified ordinary baseline, use `--pgo off`; inherited `GOFLAGS` and implicit Go profile selection are recorded but not interpreted into profile provenance.

The versioned JSON record contains:

- Driver and compiler versions, compiler path and SHA-256.
- Target Go environment and Go version, command, arguments, module directory, and effective PGO selection.
- Generated Go path and SHA-256, explicit profile path and SHA-256, and output binary SHA-256.
- Build success, errors, and whether the explicit profile was accepted by a successful Go build.
- Limitations, including unmeasured profile matching and the fact that generated-source hashes precede optional SIMD extraction.

The record identifies the generated source and selected profile; it is not a complete lockfile for native shims, transitive Go dependencies, environment variables, or external resources. Preserve those inputs separately when reproducing a build. The record uses build-time evidence for native and WASM alike. It does not depend on reading executable build information with `go version -m`. Missing profiles fail before invoking the build; corrupt profiles fail through Go's profile parser. Failed Go builds replace prior successful records with a failure record and no artifact hash. An ordinary unrecorded rebuild removes an old record. Hash checks also reject source/profile changes during the build. An existing binary may remain after failure; consult `success` and the artifact hash rather than the binary's existence.

`profile_read: true` means the explicit profile was accepted by a successful Go build, including reuse of Go's content-addressed build cache. It does not establish that application hot spots matched or that any optimization was applied. `profile_match: "not-measured"` is intentional: unrelated but valid profiles can build successfully. The format does not yet measure function/edge coverage or provide a compatibility threshold. A path identifies the input, not its training workload; retain workload descriptions and collection commands alongside the profile.

Go CPU profiles can cross OS/architecture configurations, but target-specific code and workload differences affect applicability. Native training for WASM is supported as profile input, not a guarantee of matching coverage or browser speedup. Measure the target workload and keep the toolchain versions fixed when comparing. [Go PGO documentation](https://go.dev/doc/pgo)

## Collect, merge, build, and measure

GoML does not introduce a profile file format. Collect CPU profiles using Go's `runtime/pprof` through an explicit native shim, or existing application profiling support. Preserve the generated code, build record, workload parameters, collection duration, toolchain, and machine information.

Merge existing CPU profiles with the Go tool:

```sh
go tool pprof -proto cpu.pgo pwm.pgo rtc.pgo > combined.pgo
goml build --pgo combined.pgo
```

The merge sums samples; it does not give each workload equal weight. A long SDK workload can dominate shorter synthetic profiles. Record the input hashes, original sample weights, and any explicit normalization or weighting outside this command. Do not label an unnormalized merge “equal workloads.” [Go's merging guidance](https://go.dev/doc/pgo#merging-profiles)

A public, dependency-free interpreter example and measurement entry point live under [`tools/performance`](../tools/performance). From the repository root, with Go 1.26+ on `PATH`:

```sh
python3 tools/performance/pgo.py --samples 6 --wasm
```

The script copies the example into `_artifact/performance-pgo/source`, builds a baseline, collects a native training profile, then builds the PGO executable. Optional WASM builds also finish before measurement. The script performs one excluded native warmup per executable. With `--wasm`, it then uses Node and the selected Go toolchain’s `lib/wasm/wasm_exec_node.js` to run the plain and PGO WASM artifacts once each, with the same iteration count. Their interpreter-step counts and checksums must match both native warmups. All functional checks finish before the script alternates native plain/PGO and PGO/plain measurement rounds. Each process reports an interpreter-step count, deterministic checksum, work duration, allocations, and allocated bytes. Functional results must agree. `samples.json` preserves ordered raw measurements including warmups and process wall time; `results.json` also records toolchain/machine information, profile provenance, build duration, artifact size, record paths/hashes, medians, and paired ratios. `wasm-validation.json` and the report’s `wasm_validation` field preserve the Node and Go paths/versions, executor/runtime script paths and hashes, native reference, commands, and WASM program output. Node work durations are excluded from performance comparisons.

The Node executor receives a small, recorded environment containing only `TMPDIR`, which avoids passing build-only variables into Go WASM’s limited startup argument/environment area. The example is a synthetic workload, not a browser benchmark or comprehensive compiler regression suite. Native warmup cannot stand in for browser JIT warmup. Optional WASM checks builds, records, and functional output in Node; it does not measure browser performance. `--wasm` requires Node on `PATH` and the executor shipped with the selected Go toolchain. Work duration and process wall duration remain distinct, and interpreter steps are not hardware MHz. Run measurements on an otherwise idle machine, repeat unchanged builds to assess noise, and inspect the distribution and paired ratios. No significance test or hard regression threshold is inferred; a negative throughput change is reported normally.
