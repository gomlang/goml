# Control-flow and copy optimization validation

[English](performance-validation.md) | [简体中文](performance-validation.zh-CN.md)

This change addresses the first three compiler work items from the ESP32 emulator investigation: shared control flow and size regressions, field/array copy elimination, and optional explanations with PGO build records. Browser resource loading and a complete cross-platform performance regression service are separate work.

## Reproduce the control-flow growth

The essential pattern is a sequence of conditional early exits followed by a shared continuation:

```goml
fn check(fail: bool) -> Result[(), string] {
    if fail { Err("failure") } else { Ok(()) }
}

fn work(active: bool, fail: bool) -> Result[isize, string] {
    if active { check(fail)?; }
    if active { check(fail)?; }
    println("shared-tail-marker");
    Ok(7)
}

fn main() -> () {
    let _ = work(true, false);
}
```

Repeat the conditional line to expose the growth. `defer`, generics, and a large callee are not necessary. Explicit `if fail { return Err("failure") }` produces the same pattern. Core, Mono, Lift, and ANF retain one tail. The old ANF-to-Go lowering copied the continuation into both branches because a terminating branch prevented recognition of a common target. This happens before the Go compiler runs; disabling downstream Go inlining does not remove that generated source growth.

The backend now distinguishes a terminating path from divergent jump targets. Common continuations merge after branches. When an inlined return jumps to a different continuation, nested labeled regions share the remaining join bodies without `goto` or new function calls. Join arguments remain in their enclosing scope. DCE carries break-target and continue-target liveness through those regions so that assignments used after a jump survive.

[`control_size_test.goml`](../gomlc/go_backend/control_size_test.goml) checks 2, 4, 8, and 16 conditionals, requires one static tail occurrence, limits absolute generated bytes, and checks sub-threefold growth when the input doubles. It also exercises `match` and `select`. These are deterministic size assertions, independent of CPU timing. [`shared_join_arguments_test.goml`](../gomlc/go_backend/shared_join_arguments_test.goml) verifies multiple tuple/struct jump arguments by compiling and running the generated Go.

[`project112_shared_continuations`](../gomlc/testdata/module/project112_shared_continuations/main.goml) checks 96 error/cleanup combinations, independent early returns, compound branch values, current/outer loop jumps, and cleanup during panic unwinding. The same assertions run with the pinned stage0 and the changed compiler.

The retained ESP32 generated Go input at the supplied reproducer path (46,264,513 bytes in this validation) reproduces `prepwrite: bad off=1073741824` with Go 1.26.0 and PGO disabled. It is a complete downstream reproducer, not a minimized Go compiler bug. Rebuilding the retained, unsplit GoML source with shared continuations succeeds. This avoids the pathological input; it does not claim to fix the Go compiler's diagnostic.

## Reproduce the field-read measurement

With Go 1.26 on `PATH`, after `just make`:

```sh
python3 tools/performance/projection.py --samples 6
```

The baseline defaults to `stage0/bin/gomlc`, and the candidate to `stage2/bin/gomlc`. Explicit `--baseline` and `--candidate` paths allow later comparisons. The public source reads 32 integers through a nested struct. Each benchmark call must sum to 528. It builds both variants and collects assembly, Go escape diagnostics, and a source-mapped performance explanation before timing. It then excludes a warmup and alternates baseline/candidate order, saving every raw sample and allocation count under `_artifact/performance-projection`.

Use `performance.json` to find the source declaration and its generated names, then inspect `baseline/generated.go`, `candidate/generated.go`, and their `assembly.txt` files. The old generated code copies the nested struct and the array field; array indexing also passes an array by value to a helper. Immutable field projections can now point at the existing local storage, and dynamic `array.get` calls lower to Go indexing. Constant indexes retain the helper where Go would otherwise reject a constant out-of-bounds index before the program can produce its required runtime panic.

The old `4b2498c84` branch’s immutable named-struct projection optimization is included, with fixed-array reads and direct dynamic indexing added. These internal pointers do not add source-language ownership rules. Mutation or join-parameter reassignment prevents field sharing. `Ref`/`Vec` reads, return values, and closure captures preserve value snapshots. [`project111_projection_value_semantics`](../gomlc/testdata/module/project111_projection_value_semantics/main.goml) exercises these boundaries, nested structures, CPU/bus/peripheral interaction, side effects in indexes, and constant/dynamic/discarded out-of-bounds reads. A related fix makes pointer-parameter analysis inspect assignments in every `select` arm.

## Explanations and PGO evidence

See [performance explanations and reproducible PGO builds](performance.md) for the commands, versioned JSON formats, profile weighting rules, and limitations. The report maps costs to enclosing GoML declarations and records static facts; it does not claim expression-level pprof mapping, final Go escape decisions, or measured profile coverage.

The public PGO example uses deterministic interpreter steps and a checksum, captures a native CPU profile, builds native and optionally WASM outputs, and preserves balanced raw timing samples. Native and WASM build records use build-time hashes and toolchain queries, without assuming `go version -m` can inspect every artifact. Successful profile acceptance is distinct from hot-function matching and performance improvement.

Run timing tools after compiler builds and tests have finished. Build duration is cache-sensitive; native microbenchmark improvements do not establish browser or complete-emulator gains. The scripts report regressions as well as improvements and make no single-run significance claim.

## Recorded validation

The 2026-10-23 run used Linux amd64, an Intel Core i7-13700K, Go 1.26.0, and Node 22.14.0. Native timing samples were pinned to CPU 0. Compiler/test jobs finished before measurement; editor background services remained running. Each runtime comparison excludes a warmup and retains six alternating-order rounds.

`just update-golden` and `just ci` passed, including 1,306 compiler tests, 407 driver/standard-library tests, stage3 fixed-point verification, and packaging checks. SIMD tests verify both scalar-equivalent results and retention of the expected native kernels.

For the conditional-error reproducer, the retained baseline and changed compiler produced:

| Conditions | Baseline Go bytes | Changed Go bytes | Baseline static tails | Changed static tails |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 6,360 | 5,763 | 2 | 1 |
| 2 | 9,356 | 6,641 | 4 | 1 |
| 4 | 31,906 | 8,407 | 16 | 1 |
| 8 | 620,774 | 11,969 | 256 | 1 |
| 12 | 8,694,441 | 14,219 | 4,096 | 1 |

For the 12-condition generated files, single `go build -pgo=off` observations were 1.00 s / 299,364 KiB peak RSS before and 0.08 s / 57,200 KiB after. Executable sizes were 2,221,511 and 2,154,645 bytes, and both printed the same result. These measurements use the existing Go dependency cache; they are not a statistical build-time comparison. Raw results and generated sources are under `_artifact/esp32emu-implementation/scale-final`.

The retained unsplit ESP32 module rebuilt successfully with no helper extraction. Its generated Go decreased from the retained file’s 46,264,513 bytes to 9,185,536 bytes; `run` decreased from 32,885,107 to 360,840 bytes, and direct static `Machine.step` call sites decreased from 1,008 to 1. The earlier project report’s approximately 54.35 MB is a historical measurement, not the retained file size measured here. The retained file fingerprint is `e867ea3c9b826ba71d48bdb8f474002074559e669e82aaf153389448f50a8eaf`.

The complete changed-compiler build and `--help` took one observed 13.90 s with 813,800 KiB peak RSS. The original generated file still fails with `prepwrite`; it cannot supply a runtime baseline. Against an earlier successful intermediate build, `hello` and `pwm` demos produced identical register dumps and expected step-budget errors at 10,000 virtual cycles: 324 and 10,000 retired instructions respectively. These are functional smoke checks, not emulator throughput measurements. `_artifact/esp32emu-implementation/esp32emu-final.json` records the inputs, hashes, commands, and limits.

The public field-read benchmark measured 61.77 ns/call before and 8.8585 ns/call after, with 0 B/call and 0 allocations/call in both variants. Generated Go was 5,841 versus 5,531 bytes. The report identifies `read` at `main.goml:11:4` and `project` at `main.goml:19:4`, each with one borrowed field projection. Go 1.26.0 escape diagnostics say their pointer parameters do not escape. The retained assembly shows direct indexed loads in `project` after optimization, replacing aggregate copying. The checksum remains 528. This approximately 6.97-fold throughput change applies only to this small read benchmark. Raw samples, compiler hashes, generated Go, downstream diagnostics, assembly, and the report are in `_artifact/performance-projection`.

The public PGO example deliberately reports an observed regression:

| Metric | PGO off | Native profile supplied |
| --- | ---: | ---: |
| Native median work time, 2,000,000 interpreter steps | 131.33 ms | 214.00 ms |
| Native executable bytes | 3,291,200 | 3,291,574 |
| WASM bytes | 3,772,687 | 3,772,274 |

Native throughput decreased by 38.63%; all six paired speed ratios were between 0.6126 and 0.6180. Both variants measured zero allocations in the work interval. Training used 40,000,000 interpreter steps. All four build records contain the same generated-source hash, and both supplied-profile builds report successful profile acceptance. Profile coverage remains unmeasured; the cause of this downstream PGO regression has not been isolated.

Native, plain WASM, and PGO WASM all produced checksum `5556bcccd558a435` for 2,000,000 interpreter steps. WASM was executed in Node for correctness only; its raw times are excluded from the performance comparison. `_artifact/performance-pgo/results.json`, `samples.json`, `wasm-validation.json`, and the four `.build.json` files retain the evidence. This example demonstrates collection, application, target validation, and reporting of degradation without promising a speedup.
